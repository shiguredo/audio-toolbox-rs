# デコード経路で出力バッファと `mDataByteSize` を整合させ、異常時はエラーにし Rust 側の誤用を防ぐ

Created: 2026-04-01
Completed: 2026-04-01
Model: Claude Opus 4.5

**スコープ:** 本ブランチのミッションは **パニック・セグメンテーションフォルト（および FFI による未定義動作）** の防止に限定する。

## なぜこの対応が必要か

`Decoder::decode_impl` は `AudioConverterFillComplexBuffer` に **`pcm_buf` のポインタとバッファサイズ**を渡し、成功**後**に `mDataByteSize` を読む。

**C 側・FFI（事後検証では「未然防止」にならない）:** フレームワークが **渡したバッファの範囲を超えて `mData` に書き込む**場合、**その書き込みの時点で**ヒープ越境・**セグフォ・未定義動作**は既に起きうる。呼び出し**後**の検証は **実書き込み越境そのものを取り消さない**。

**Rust 側の整合性・異常値:** 現行コードは `byte_size` からサンプル数 `size` を求め `pcm_buf.truncate(size)` する。`Vec::truncate` は **新しい長さが現在の `len` 以上**のとき **何もしない**（**パニックもしない**）。したがって本 issue の主眼は **`truncate` によるパニック防止ではない**。問題は **`mDataByteSize` が実バッファ（バイト）や `pcm_buf.len()`（i16 サンプル数）と矛盾する異常値**のとき、**縮めずにフル長の `Vec` を返す**等、**誤った長さの PCM を返しうる**こと、および **`byte_size` が `i16` フレーム境界と合わない**場合の**長さ解釈のゆれ**である。これらを **検証して異常時は `Result::Err` 等に落とす**ことが、本 issue の Rust 側の受け入れに近い。

**将来のコードパス:** 現行以外で **`mDataByteSize` をそのままスライス長に使う**変更が入った場合は、**境界外スライスでパニック**しうるため、**一箇所に集約した検証**と併せて考える。

## 既存 issue との関係

- `issues/0002-investigate-decoder-output-buffer-vs-codec-limits.md` は定数・理論上限の調査。本 issue は **実行時の `mDataByteSize` とバッファ境界**の検証。

## 受け入れ条件の目安

- 返却された `mDataByteSize`（および導出するサンプル数）が **確保した出力バッファを超えない**ことを検証し、異常時は **`Result::Err`**（パニックにしない）。
- `0002` の定数方針と矛盾しないこと。

## ミッション適合性の確認

- **適合する。** 根拠: **FFI 実書き込み越境**は **セグフォ・UB**。**Rust 側**では **`mDataByteSize` とバッファ境界の不整合**を **明示的に扱わないと誤った長さの返却**につながりうる（現行は **パニックより論理バグ**が主）。0004 と同様、**C 側は「検出・以降の誤用防止」、Rust 側は「境界・整合の検証」**に分けて書く。
- **0002 との差分:** `0002` は **定数・理論上限**の調査が中心。本 issue は **実行時の `mDataByteSize` と実バッファ**の整合。
- **注意:** **`Vec::truncate` は `new_len >= len` でパニックしない**（事実誤認を issue 本文に残さない）。

## 参考（該当コード）

- `src/lib.rs`: `decode_impl`、`DECODE_BUF_FRAMES`、`OUTPUT_CHANNELS`

## 解決方法

- `Decoder::decode_impl` で、返却 `mDataByteSize`（バイト）が `pcm_buf` の容量（バイト）を超えないこと、`i16` 境界（2 バイト単位）であること、導出サンプル数が `pcm_buf.len()` を超えないことを検証し、異常時は `kAudio_ParamError` 相当の `Error` を返すようにした。
